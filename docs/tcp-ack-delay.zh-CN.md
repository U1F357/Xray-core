# 初始连接窗口内的 ACK 最早确认时间

> fp-v0.7.0 修正计时语义。fp-v0.6.0 使用的是逐包追加等待；下面描述新实现。

适用于 Linux gVisor 指纹出口。配置示例：

```json
{
  "protocol": "freedom",
  "settings": {
    "tcpFingerprint": "auto",
    "tcpECN": "auto",
    "tcpAckDelay": {
      "minMs": 80,
      "maxMs": 120,
      "continuous": true
    }
  }
}
```

`tcpFingerprint` 也可选择 `windows`、`macos`、`linux`。

## 时间窗口与随机方式

- 默认关闭；省略 `tcpAckDelay` 不启用；手动模式的 `maxMs: 0` 关闭 ACK 调度。自动模式见 [入口 RTT](tcp-rtt.zh-CN.md)。
- `minMs`、`maxMs` 为闭区间的整数毫秒，要求 `0 <= minMs <= maxMs <= 1000`。
  每段新收到的服务器序列空间独立抽取一个最小确认年龄；相等表示固定值。
- `continuous: true` 表示整条连接持续生效，不能同时配置非零 `windowMs`。
- 不启用 continuous 时，`windowMs` 省略或为 0 是 **10000 ms**，最大 60000 ms。
- 从该连接第一次有效 SYN-ACK 原始到达时开始计时。
  它自己的等待时间也在这 10 秒内，不是在握手完成后再增加 10 秒。
- 生效期间，纯 ACK、携带 TLS/应用数据的 ACK、FIN+ACK、携带 ECN
  反馈的 ACK 都根据其实际确认的累计 ACK/SACK 范围经过调度。SYN 直接发送；RST 优先直接发送，并丢弃该连接排队数据。
- 到期后不再记录新的最早确认时间；已排队包按原截止时间发完，新包排在其后，避免切换
  造成乱序。正常情况下这一尾部等待不超过 `maxMs`，系统调度或设备拥塞可能更久。
- 同连接严格保持原发包顺序，新包不能越过前面的包（包括已到期但尚未送出的包）。
  截止时间为 `max(当前时间, 所确认数据的首次接收时间 + 抽取值, 前包计划发送时间)`。
  已花费在客户端往返的时间自然被扣除，不再从出站包生成时额外等待完整区间。

## 与旧握手延迟的关系

开启 `tcpAckDelay` 后，**旧 `tcpHandshakeDelay` 的 SYN-ACK 暂存不再执行**，即使
旧配置仍保留。新模式使用同一接收截止时间暂存 SYN-ACK，并约束后续 ACK；两者
不叠加。只配置旧选项时，仍保持 fp-v0.5.1 的仅握手行为。

握手暂存也让 gVisor 初始 RTT/RTO 包含等待，避免先按极短 RTT 启动重传计时器、
再把 ClientHello 扣在发包队列里。握手只等到同一个截止时间，不重复叠加。

## 连接复用与边界

- 每条 TCP 连接只启动一次窗口；HTTP keep-alive、HTTP/2 stream、新 HTTP 请求
  都不会重置窗口。TCP 新连接重新计时。
- 不解析或解密 TLS，也不保证任意延迟开始的 TLS 都位于窗口内。
- IPv4/IPv6 均适用，支持常见 IPv6 扩展头。无法解析或分片报文直接交给原路径；
  正常 gVisor TCP 出口按 MTU 分段。UDP/QUIC 和普通系统 TCP 出口不受影响。
- 使用每栈一个异步计时调度器，不在读包/发包循环中等待延迟计时器。
- 内存上限为每连接 4 MiB、每栈 32 MiB、每栈 16384 个排队包及 16384 个受控连接。
  队列满时丢弃新包并记录限频警告，由 TCP 重传恢复，绝不无上限积压。
  不同平台/地址族的栈分别计算限额。
- RST、元组复用会清理旧队列；core 关闭会取消调度。未完成握手的状态最多保留约
  30 秒，限时模式的状态在窗口结束且队列排空后清理；持续模式在完整 Close 后有约 30 秒清理宽限期，空闲清理周期约一秒。

INFO 日志显示上下限、窗口、continuous 及 `includesHandshake=true`；
队列压力会产生 WARNING。`mode=minimumAcknowledgmentAge` 表示新语义。窗口和限幅由本地 freedom 配置；自动模式可接收可信 VLESS 传来的入口 RTT。

## 预期效果与验证

这是人为增加前期确认/发送等待，会影响目标测得的部分 RTT、TCP 拥塞控制和应用
时延。包括数据的 ACK 都延迟，因此不能同时保证 RTT 增加且应用零开销；尤其是
短连接，其全部传输可能都落在窗口内。建议从 80–120 ms 开始测试，过大的延迟
会触发重传。不能保证网站始终显示升高的 RTT，窗口后的测量可能恢复较低数值。

测试覆盖随机范围、有序调度、窗口切换、并发隔离、取消、RST/元组复用、队列
上限、旧握手配置不叠加，以及九种平台/ECN 组合下 IPv4/IPv6 的持续 TLS 传输。
抓包核对初始握手和数据 ACK 延迟：限时模式超过 10 秒恢复正常，持续模式仍保持确认年龄。

## 确认时间关联与后续数据

调度器在 TUN 收包后、注入 gVisor 前，记录服务器 SYN、数据和 FIN 消耗的序列
区间。它处理序列号回绕、部分确认、乱序/SACK 和重叠重传；同一字节首次收到后
不因重复报文重新计时，只有 ACK 实际发出后才删除相应记录。

例如，确认年龄固定 100 ms：本地立即生成的 ACK 等待接近 100 ms；客户端回复
在 70 ms 后到达，剩余等待接近 30 ms；在 110 ms 后才到达，就不再额外等待。
如果回复同时确认了后来新收到的数据，仍需遵守新数据的截止时间；不能保证每个
TLS/应用回复都零等待。重复确认已发出 ACK 的数据也不会重新启动 100 ms 等待。

每连接最多记录 128 个接收区间，每栈最多 65536 个；达到上限时退回有界的保守
截止时间（最近一次无法记录的接收时间 + maxMs），记录警告，仍受所配置的窗口约束。
因此在区间跟踪溢出时，避免重复追加等待的精确性会下降，不会无限增加内存。

后续非 TLS 数据使用同一规则，不解密应用协议。持续开启仍会影响下载确认、拥塞
控制和吞吐，可以选择持续模式，或使用限时模式控制开销。

回归测试额外使用 netem 模拟客户端 RTT 100 ms、出口 RTT 1 ms，固定最小确认
年龄 100 ms；比较服务器数据 ACK 和首个客户端加密 TLS 响应的到达时间，并支持
以 fp-v0.6.0 二进制作追加等待的对照。该实验使用已知的 TLS 1.3 测试握手流程，
不代表实现能够解密识别任意真实连接的 Finished。

VLESS 缓冲、普通客户端兼容性与实现细节见 [时序设计](tcp-timing-design.zh-CN.md)。
