# 初始连接窗口内的 ACK 随机延迟（fp-v0.6.0）

适用于 Linux gVisor 指纹出口。配置示例：

```json
{
  "protocol": "freedom",
  "settings": {
    "tcpFingerprint": "auto",
    "tcpECN": "auto",
    "tcpAckDelay": {
      "minMs": 80,
      "maxMs": 120,
      "windowMs": 10000
    }
  }
}
```

`tcpFingerprint` 也可选择 `windows`、`macos`、`linux`。

## 时间窗口与随机方式

- 默认关闭；省略 `tcpAckDelay` 或设置 `maxMs: 0` 不启用。
- `minMs`、`maxMs` 为闭区间的整数毫秒，要求 `0 <= minMs <= maxMs <= 1000`。
  每个 ACK 包独立均匀抽取延迟；相等表示固定延迟。
- `windowMs` 省略或为 0 时是 **10000 ms**，最大 60000 ms。
- 从该连接的第一个出站 ACK 进入调度器时开始计时，一般就是第三次握手 ACK。
  它自己的等待时间也在这 10 秒内，不是在握手完成后再增加 10 秒。
- 生效期间，纯 ACK、携带 TLS/应用数据的 ACK、重传 ACK、FIN+ACK、携带 ECN
  反馈的 ACK 都经过调度。SYN 直接发送；RST 优先直接发送，并丢弃该连接排队数据。
- 到期后不再为新包抽取延迟；已排队包按原截止时间发完，新包排在其后，避免切换
  造成乱序。正常情况下这一尾部等待不超过 `maxMs`，系统调度或设备拥塞可能更久。
- 同连接严格保持原发包顺序；某包抽到短延迟时，也不能越过前面的包。延迟不是
  按包串行累加，而是使用 `max(当前时间 + 抽取值, 前包计划发送时间)`。

## 与旧握手延迟的关系

开启 `tcpAckDelay` 后，**旧 `tcpHandshakeDelay` 的 SYN-ACK 暂存不再执行**，即使
旧配置仍保留。新模式直接延迟第三次握手 ACK，使用同一组 `minMs/maxMs`；两者
不叠加。只配置旧选项时，仍保持 fp-v0.5.1 的仅握手行为。

由于新模式是出口发包调度，gVisor 可能已在本地完成建连，而第三次 ACK 尚未
实际写入 TUN。ClientHello 等后续包也经过同一有序队列，不会越过它。

## 连接复用与边界

- 每条 TCP 连接只启动一次窗口；HTTP keep-alive、HTTP/2 stream、新 HTTP 请求
  都不会重置窗口。TCP 新连接重新计时。
- 不解析或解密 TLS，也不保证任意延迟开始的 TLS 都位于窗口内。
- IPv4/IPv6 均适用，支持常见 IPv6 扩展头。无法解析或分片报文直接交给原路径；
  正常 gVisor TCP 出口按 MTU 分段。UDP/QUIC 和普通系统 TCP 出口不受影响。
- 使用每栈一个异步计时调度器，不在读包/发包循环中等待延迟计时器。
- 内存上限为每连接 4 MiB、每栈 32 MiB、每栈 16384 个排队包及 16384 个受控连接。
  队列满时丢弃新包并记录限频警告，由 TCP 重传恢复，绝不无上限积压。
  不同平台/地址族的栈分别计算限额。
- RST、元组复用会清理旧队列；core 关闭会取消调度。未完成握手的状态最多保留约
  30 秒，已完成连接的状态在窗口结束且队列排空后清理，空闲清理周期约一秒。

INFO 日志显示上下限、窗口及 `includesHandshake=true replacesSYNACKDelay=true`；
队列压力会产生 WARNING。窗口和上下限只由本地 freedom 配置，不经 VLESS 传递。

## 预期效果与验证

这是人为增加前期确认/发送等待，会影响目标测得的部分 RTT、TCP 拥塞控制和应用
时延。包括数据的 ACK 都延迟，因此不能同时保证 RTT 增加且应用零开销；尤其是
短连接，其全部传输可能都落在窗口内。建议从 80–120 ms 开始测试，过大的延迟
会触发重传。不能保证网站始终显示升高的 RTT，窗口后的测量可能恢复较低数值。

测试覆盖随机范围、有序调度、窗口切换、并发隔离、取消、RST/元组复用、队列
上限、旧握手配置不叠加，以及九种平台/ECN 组合下 IPv4/IPv6 的持续 TLS 传输。
抓包核对初始握手和数据 ACK 延迟，并确认同一连接超过 10 秒后恢复正常。
